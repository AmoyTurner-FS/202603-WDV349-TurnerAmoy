## Topic - Project Clarification & Kickoff

This week I focused on reviewing the CarFinder project and making sure the idea, scope, and overall direction still made sense before starting development. Since this project is carrying over from a previous course, I wanted to look at what has already been completed and make sure the remaining work is still realistic.

<br>

## Sub-Topic 1 - Building a Business Case

One thing I learned is that before development begins, there should be a clear reason for why the project is being built. A project proposal should explain the problem, who the application is for, what value it provides, and what the overall goals are.

For CarFinder, the main goal is to give users a simple way to search for vehicles by year, make, and model without having to go through a lot of unnecessary information. Reviewing the project this way helped confirm that the idea still has a clear purpose and target user.

<br>

## Sub-Topic 2 - Discovery

The discovery process happens before major development and helps clarify what is actually needed. Instead of immediately starting to code, discovery focuses on asking questions about the project, users, goals, risks, and features.

Some of the questions I considered for CarFinder were:

* Who is the application mainly being built for?
* What problem is CarFinder solving?
* Which features are most important to complete first?
* What parts of the project have already been completed?
* What technical or development challenges could affect the project?
* What would make the finished application successful?

This process helped me look at the project as a whole instead of only focusing on individual coding tasks.

<br>

## Sub-Topic 3 - Evaluating the Project Idea

Another part of the research focused on evaluating whether an idea is worth continuing. A project should solve a real problem and provide enough value for someone to actually want to use it.

CarFinder is not meant to compete with every feature offered by larger vehicle websites. The main value of the project is simplicity. Instead of focusing on financing, dealerships, advertisements, and other features, CarFinder focuses on helping users quickly search and explore vehicle information.

I think the project is still a good fit because it is realistic for the time available and gives me the opportunity to demonstrate frontend development, backend development, API integration, database work, and project management.

<br>

## Sub-Topic 4 - Project Kickoff

A project kickoff happens after the overall direction and scope are clear enough for development to move forward. By this point, the team should understand what is being built, why it is being built, what technology will be used, and what work needs to be completed.

Since CarFinder is continuing from a previous course, this week is more like a second kickoff. I am reviewing the original proposal, tech stack, existing designs, and GitHub issues before continuing development. Any changes to the original scope will be documented before they are added to the project.

<br>

## Sub-Topic 5 - 30 Second Pitch

A 30 second pitch should explain the project quickly enough that someone who has never seen it can understand the idea and why it matters.

### CarFinder Pitch

CarFinder is a web application that gives users a simple way to search for vehicles by year, make, and model. The goal is to make vehicle research easier by focusing on the information users are actually looking for without adding a lot of unnecessary features. The application will use a React frontend, backend API, external vehicle data, and a database to create a complete full stack experience.

<br>

## What I Learned

The biggest thing I took away from this research is that development should not begin without first making sure the project still has a clear purpose and realistic scope. Since I am returning to an existing project, reviewing the original idea before continuing helps me avoid adding features that do not support the main goal.

I also understand why discovery, project planning, and GitHub issues are important. Breaking the remaining work into smaller tasks makes it easier to track progress and keeps the project from becoming overwhelming.
